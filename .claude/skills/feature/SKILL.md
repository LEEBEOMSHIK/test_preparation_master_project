# /feature — 5단계 에이전트 파이프라인 오케스트레이션

이 스킬은 신규 기능을 **분석 → 설계 → (승인) → 구현 → 검증 → 테스트** 순서로 끝까지 운영한다.
새로운 분석/구현 로직을 직접 수행하지 않는다 — 기존 5개 에이전트(`codebase-explorer`, `webapp-planner`, `webapp-developer`, `webapp-verifier`, `webapp-tester`)를 **지휘**한다.

진행 방식은 **모드 B(설계 승인 게이트)**: 설계 산출 후 한 번 멈춰 사용자 승인을 받고, 승인되면 구현~테스트까지 자동 진행한다.

비용 절감을 위해 이 스킬은 기본 워크플로우가 아니라 고신뢰 모드로 사용한다. 화면·메뉴·파일·API가 명확한 작업은 먼저 해당 경로에서 좁게 탐색하고 직접 처리하며, 이 스킬은 사용자가 `/feature`를 명시했거나 신규 API/DB/보안/공통 유틸처럼 실패 비용이 큰 다중 레이어 작업에만 적용한다.

---

## 사용 판단 (스킬 시작 전 자가 점검)

- **사용함**: 사용자가 명시적으로 `/feature`를 요청한 작업, 다중 레이어(FE/BE/DB)에 걸친 신규 기능, 신규 API/DB/보안/공통 유틸처럼 실패 비용이 큰 풀스택 기능.
- **사용 안 함**: 단일 파일 1~2줄 수정, 오타/스타일 수정, 단순 질문. → 파이프라인 없이 직접 처리하고, 이 스킬을 호출하지 않는다.
- **먼저 좁게 탐색**: 사용자가 화면·메뉴·파일·API를 명시한 경우, 관련 라우트/컴포넌트/서비스/Controller/Entity부터 확인하고 영향 범위가 실제로 넓을 때만 이 스킬로 확장한다.

요구사항이 모호하면(대상 화면·범위 불명확) **스킬 시작 전에** 한 가지 핵심 질문으로 명확히 한다.

---

## 진행 절차

진행 상태를 가시화하기 위해 **시작 시 TaskCreate로 5개 태스크**를 만든다(분석/설계/구현/검증/테스트). 각 단계 진입 시 `in_progress`, 완료 시 `completed`로 TaskUpdate 한다.

### 1단계 — 분석 (codebase-explorer)
`Agent`(subagent_type: `codebase-explorer`)로 다음을 조사한다:
- 관련 Entity·테이블·기존 API·서비스 레이어·컴포넌트·유사 구현
- 영향받는 파일과 재사용 가능한 공통 자산(`src/lib/`, `src/components/ui/`)

분석 결과를 요약해 다음 단계 입력으로 보관한다.

### 2단계 — 설계 필요 여부 판단 (자동 게이트)
다음 중 하나라도 해당하면 설계(3단계) 진행, 아니면 4단계로 건너뜀:
- 수정 파일 3개 이상 + 파일 간 의존관계 있음
- 기존 연결 방식이 분석만으로 불명확
- 구현 방식 선택지 2개 이상(트레이드오프 필요)

건너뛰는 경우: "설계 단계는 단순 작업이라 생략합니다"를 한 줄 알리고 4단계로 간다.

### 3단계 — 설계 (webapp-planner)
`Agent`(subagent_type: `webapp-planner`)에 1단계 분석결과를 전달해 계획을 산출한다.
산출물: 작업 요약 / 영향 범위(FE·BE·DB) / 아키텍처 결정·대안 / 단계별 구현 계획 / 컨벤션 체크리스트 / 검증·테스트 계획 / 리스크.

### ★ 승인 게이트 (모드 B) — 여기서 반드시 멈춘다
설계 요약을 사용자에게 제시하고, **승인 없이는 구현으로 넘어가지 않는다.**
`AskUserQuestion`으로 다음을 묻는다:
- 옵션: "이대로 구현 진행" / "수정 후 진행"(어디를 바꿀지 받음) / "중단"
- "수정 후 진행"이면 피드백을 반영해 webapp-planner에 재설계를 요청하고 다시 이 게이트로 돌아온다.
- "중단"이면 여기서 종료한다.

> 이유: 설계가 틀리면 그 위의 구현·검증·테스트가 전부 헛수고가 된다. 가장 싼 지점에서 한 번 끊는다.

### 4단계 — 구현 (webapp-developer)
`Agent`(subagent_type: `webapp-developer`)에 승인된 계획을 전달해 구현한다.
**이때 반환된 `agentId`를 반드시 보관한다** — 이후 검증/테스트 되돌림에서 이 에이전트를 `SendMessage`로 이어 써야 맥락이 유지된다.
구현 에이전트는 코드 작성 + 히스토리 파일 자동 작성까지 수행한다.

### 5단계 — 검증 (webapp-verifier, 정적)
`Agent`(subagent_type: `webapp-verifier`)로 컨벤션·타입·누락·히스토리·보안을 정적 점검한다.
- **이상 없음** → 6단계로.
- **이상 발견** → 4단계에서 보관한 developer `agentId`에 **`SendMessage`로 수정 요청**(새 Agent 스폰 금지). 수정 완료 후 **다시 5단계** 재검증. 통과할 때까지 반복(과도하면 사용자에게 보고).

### 6단계 — 테스트 (webapp-tester, 동적)
`Agent`(subagent_type: `webapp-tester`)로 실제 빌드·테스트·타입체크를 실행한다(`./gradlew test`, `npx tsc --noEmit`, `npm run build` 등).
- **전부 통과** → 7단계로.
- **실패** → 5단계와 동일하게 developer `agentId`에 `SendMessage`로 수정 요청 → **다시 6단계** 재테스트. 통과할 때까지 반복.
  - 단, 실패 원인이 이번 기능과 **무관한 선재 결함**(예: 기존 페이지의 빌드 오류)이면 자동으로 고치지 말고 사용자에게 보고 후 처리 방향을 묻는다.

### 7단계 — 완료 보고
- 생성/수정한 파일 목록
- 작성된 히스토리 파일(HIST ID)
- 통과한 검증·테스트 결과
- 후속 필요 작업(예: 메뉴 DB 등록, 마이그레이션 등)

---

## 되돌림 루프 핵심 규칙

- 검증·테스트 실패 시 **항상 같은 developer 에이전트를 `SendMessage`로 이어서** 수정한다. 새 `Agent` 스폰은 구현 맥락을 잃으므로 금지.
- 수정 후에는 **실패가 난 단계부터** 다시 검증한다(검증 실패면 5단계, 테스트 실패면 6단계 재실행).

## 이 스킬이 하지 않는 것

- 커밋·push는 하지 않는다. 완료 보고 후 사용자가 별도로 요청할 때만 진행한다.
- 사소한 수정에는 쓰지 않는다(위 "사용 판단" 참조).
- 새로운 분석/구현 로직을 직접 수행하지 않는다 — 전부 5개 에이전트에 위임한다.
