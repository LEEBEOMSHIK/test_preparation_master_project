# Modification History Policy

코드 수정이 발생할 때마다 반드시 히스토리 파일을 생성/갱신한다.
사용자가 별도로 요청하지 않아도 자동으로 작성한다.

---

## 저장 경로

| 범위 | 저장 경로 |
|------|-----------|
| 사용자 프론트엔드 | `docs/history/front/usr/` |
| 사용자 백엔드 | `docs/history/back/usr/` |
| 관리자 프론트엔드 | `docs/history/front/adm/` |
| 관리자 백엔드 | `docs/history/back/adm/` |

하나의 수정이 여러 범위에 걸칠 경우 각 해당 경로에 모두 기록한다.

---

## 파일명 및 ID 규칙

- 파일명: `{MenuName}_Modified.md` (예: `ExamList_Modified.md`)
- 같은 메뉴의 히스토리는 하나의 파일에 누적 추가 (최신 항목을 파일 상단에)
- ID: `HIST-{YYYYMMDD}-{3자리 순번}` (예: `HIST-20260418-001`)

### ★ 채번 규칙 — 파일별(file-scoped) 순번

- **순번은 "그 파일 내"에서만 유일하면 된다.** 새 항목 ID = `해당 파일의 같은 날짜 최대 순번 + 1`.
- **전역 순번이 아니다.** 같은 날 서로 다른 파일이 동일한 순번(예: `HIST-20260613-001`)을 갖는 것은 **정상이며 의도된 동작**이다. 한 수정이 여러 범위(front/usr, back/usr 등)에 걸쳐 각 파일에 기록될 때도 각 파일이 독립적으로 채번한다.
- 따라서 **ID는 항상 "어느 파일(메뉴)"인지와 함께 인용한다.** ID 단독으로는 전역 유일하지 않다 (예: "front/usr `DailyQuiz_Modified.md`의 `HIST-20260613-002`").
- 채번 전 반드시 **해당 파일의 맨 위 항목을 읽어** 그 날짜의 현재 최대 순번을 확인하고 +1 한다. 추측으로 순번을 쓰지 않는다.

## 히스토리 파일 템플릿

```markdown
## HIST-YYYYMMDD-NNN

- **날짜**: YYYY-MM-DD
- **수정 범위**: (예: 관리자 백엔드 / 시험 관리)
- **수정 개요**: 한 줄 요약

### 수정 파일 목록

| 파일 경로 | 수정 유형 | 설명 |
|-----------|-----------|------|
| path/to/File.java | 추가/수정/삭제 | 변경 내용 요약 |

### 수정 상세

#### `path/to/File.java`
- 변경 전: (핵심 코드 또는 상태 요약)
- 변경 후: (핵심 코드 또는 상태 요약)
- 이유: 변경 이유

### 복원 방법

이 ID(`{MenuName}_Modified.md` 기준 HIST-YYYYMMDD-NNN)로 복원 시 위 "수정 상세"의 "변경 전" 내용을 각 파일에 적용한다. (순번은 파일별이므로 복원 시 파일명도 함께 지정한다.)
```

---

## AI 행동 규칙

1. 코드를 수정하기 **전에** 해당 메뉴/범위를 파악한다.
2. 수정 완료 **후** 즉시 히스토리 파일을 생성 또는 갱신한다.
3. 복원 요청 시 (파일명 + 히스토리 ID)를 기준으로 "변경 전" 내용을 찾아 되돌린다.

### ★ 작성 시 무결성 규칙 (파일 손상 방지)

4. **기존 항목을 절대 덮어쓰거나 삭제하지 않는다.** 새 항목은 파일 **맨 위에 prepend**만 한다. 기존 항목·다른 날짜 항목은 그대로 보존한다.
5. **파일 전체를 재작성(overwrite)하지 않는다.** 항상 "기존 내용 위에 새 항목 추가" 방식으로만 편집한다 (예: 기존 최상단 항목을 old_string으로 매칭해 그 앞에 새 항목 삽입).
6. 채번 충돌 방지: 새 항목을 쓰기 직전 파일 최상단을 다시 읽어, 같은 날짜의 동일 순번이 이미 있으면 +1 하여 **같은 파일 내 ID 중복을 만들지 않는다.**
7. 한 작업이 여러 범위 파일에 기록될 때, 각 파일은 **자기 파일 기준**으로 독립 채번한다 (파일 간 순번을 맞추려 하지 않는다).
