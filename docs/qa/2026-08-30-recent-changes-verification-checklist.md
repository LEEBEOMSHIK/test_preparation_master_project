# 최근 변경사항 사용자 검증 체크리스트

## 목적

2026-08-30까지 반영된 관리자 문의 이메일 이력 필터, 문의·요청 처리, 이메일 알림, 패치노트, 관심시험 표시 변경을 사용자가 실제 화면에서 확인하기 위한 체크리스트다. 각 항목은 **행동**과 **기대 결과**를 함께 확인한다.

- **필수 회귀검증**: 이번 변경 또는 핵심 업무 흐름이 다시 깨지지 않았는지 반드시 확인한다.
- **권장 검증**: 다양한 데이터·화면 크기·예외 조건에서도 사용성이 유지되는지 확인한다.

## 사전 준비

- [ ] 관리자 계정과 일반 사용자 계정을 각각 준비한다.
- [ ] 한 문의에 `SENT`와 `FAILED` 등 서로 다른 상태의 이메일 이력이 함께 존재하도록 준비한다.
- [ ] 서로 다른 문의에 `FAILED` 이메일 이력이 각각 하나 이상 존재하도록 준비한다.
- [ ] 이메일 실패를 재현할 수 있는 테스트 SMTP 설정 또는 실패 이력 데이터를 준비한다.
- [ ] 관리자 이메일 수신자를 두 개 이상 등록할 수 있는 테스트 이메일 주소를 준비한다.
- [ ] 공개·비공개 패치노트와 페이지 이동을 확인할 수 있는 충분한 패치노트 데이터를 준비한다.
- [ ] 관심시험을 두 개 이상 등록하고 라이트 모드·다크 모드·모바일 화면을 확인할 수 있는 브라우저를 준비한다.

## 1. 관리자 이메일 발송 이력 복합 필터

### 필수 회귀검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 관리자 문의 상세에서 특정 문의 ID만 적용해 이메일 이력을 조회한다. | 선택한 문의의 이력만 표시되고 해당 문의에 속한 여러 발송 상태가 정상적으로 함께 표시된다. |
| [ ] | 문의 ID를 해제하고 상태를 `FAILED`만 선택한다. | 모든 문의 중 실패한 이메일 이력만 표시되고 `SENT`·`PENDING` 이력은 표시되지 않는다. |
| [ ] | 특정 문의 ID와 `FAILED` 상태를 동시에 적용한다. | 선택한 문의에 속한 실패 이력만 표시된다. |
| [ ] | 같은 문의에 `SENT`와 `FAILED` 이력이 있는 상태에서 복합 조건을 적용한다. | `FAILED`만 남고 같은 문의의 다른 상태가 섞이지 않는다. |
| [ ] | 조회 결과의 생성 시각을 위에서 아래로 비교한다. | 가장 최근에 생성된 이력이 항상 위에 표시된다. |
| [ ] | 실패 이력에서 재시도를 실행하고 목록을 다시 조회한다. | 재시도 요청이 정상 접수되고 처리 결과가 이력 상태에 반영되며 다른 문의의 이력에는 영향을 주지 않는다. |

### 권장 검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 이력이 없는 문의 ID와 `FAILED`를 동시에 적용한다. | 오류 없이 빈 상태가 표시된다. |
| [ ] | 필터 결과가 여러 페이지가 되도록 데이터를 준비해 다음 페이지로 이동한다. | 복합 필터가 유지된 채 해당 조건의 다음 결과가 표시된다. |
| [ ] | 재시도할 수 없는 상태의 이력에서 재시도를 시도한다. | 허용되지 않은 재시도가 차단되고 기존 이력 상태가 보존된다. |

## 2. 문의·요청 접수 및 처리

### 필수 회귀검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 사용자 문의 작성 화면의 유형 목록을 연다. | 일반 문의, 버그 신고, 시험 개설 요청, 신규 기능 요청을 선택할 수 있다. |
| [ ] | 버그 신고를 선택하고 발생 영역을 비운 채 등록한다. | 발생 영역 필수 안내가 표시되고 등록되지 않는다. |
| [ ] | 버그 신고의 발생 영역과 상세 위치·재현 내용을 입력해 등록한다. | 선택한 영역과 작성 내용이 사용자·관리자 상세 화면에 정확히 표시된다. |
| [ ] | 시험 개설 요청과 신규 기능 요청을 각각 선택한다. | 버그 발생 영역 같은 불필요한 입력을 강제하지 않고 유형에 맞는 요청을 등록할 수 있다. |
| [ ] | 일반 문의를 관리자가 답변 완료로 변경한다. | 일반 문의의 최종 상태가 `답변 완료`로 표시된다. |
| [ ] | 버그·시험 개설·신규 기능 요청을 각각 처리 완료와 처리 불가로 변경한다. | 요청 유형에는 `처리 완료`·`처리 불가` 상태가 적용되고 일반 문의용 상태와 혼동되지 않는다. |
| [ ] | 최종 처리 전 관리자가 메시지를 보내고 사용자가 다시 답변한다. | 양쪽 메시지가 작성 시각 순서대로 타임라인에 표시된다. |
| [ ] | 문의 또는 후속 메시지에 이미지를 첨부해 전송한다. | 허용된 이미지가 정상 업로드되고 상세 화면에서 확인할 수 있다. |

### 권장 검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 종료된 문의에서 추가 메시지와 허용되지 않은 상태 변경을 시도한다. | 종료 상태 정책에 맞게 입력 또는 상태 변경이 제한된다. |
| [ ] | 종료된 문의를 관리자 기능으로 다시 연다. | 문의가 열린 상태로 변경되고 후속 대화를 계속할 수 있다. |
| [ ] | 모바일 화면에서 문의 작성·상세·타임라인을 확인한다. | 입력란, 첨부, 상태, 메시지가 잘리거나 겹치지 않는다. |

## 3. 이메일 알림 및 재처리

### 필수 회귀검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 관리자 이메일 수신자를 두 명 이상 등록한 뒤 새 문의를 작성한다. | 활성화된 모든 관리자 수신자에게 각각 알림 발송이 시도되고 개별 이력이 남는다. |
| [ ] | 사용자가 문의에 후속 메시지를 작성한다. | 관리자 알림이 발송되고 문의·이벤트 정보가 올바르게 포함된다. |
| [ ] | 관리자가 사용자에게 답변할 때 이메일 발송을 선택하지 않고 전송한다. | 화면 메시지는 등록되지만 사용자 이메일 발송 이력은 생성되지 않는다. |
| [ ] | 같은 동작에서 이메일 발송을 선택하고 전송한다. | 문의 소유자의 이메일로 알림 발송이 시도되고 발송 이력이 생성된다. |
| [ ] | 답변 완료·처리 완료·처리 불가 변경 시 이메일 발송 선택 여부를 각각 확인한다. | 관리자의 선택에 따라서만 사용자 이메일 발송이 시도된다. |
| [ ] | SMTP 실패를 발생시킨다. | 문의·메시지 처리는 보존되고 이메일 이력은 `FAILED`로 기록된다. |
| [ ] | `FAILED` 이력을 재시도한다. | 재시도가 접수되고 성공 또는 재실패 결과가 같은 발송 업무 흐름에 반영된다. |

### 권장 검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 중복된 관리자 이메일 주소 또는 잘못된 형식의 주소를 저장한다. | 설정 검증 정책에 따라 중복·잘못된 주소가 저장되지 않거나 명확한 안내가 표시된다. |
| [ ] | 관리자 수신 알림을 비활성화한 뒤 새 문의를 등록한다. | 문의는 정상 등록되지만 관리자 이메일 발송은 시도되지 않는다. |
| [ ] | 발송 실패 후 SMTP를 복구하고 재시도한다. | 복구 후 발송에 성공하고 최신 상태와 시각을 확인할 수 있다. |

## 4. 패치노트

### 필수 회귀검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 로그인 후 전역 메뉴의 패치노트 아이콘을 선택한다. | 도움말 하위 경로를 거치지 않고 패치노트 목록으로 바로 이동한다. |
| [ ] | 이미 확인한 패치노트를 포함해 과거 목록을 연다. | 읽음 여부와 무관하게 공개된 과거 패치노트를 언제든 확인할 수 있다. |
| [ ] | 목록의 날짜와 표시 순서를 확인한다. | 최신 패치노트가 위에 표시되고 수정 목록을 별도 상세 이동 없이 확인할 수 있다. |
| [ ] | 패치노트가 한 페이지를 넘는 상태에서 페이지를 이동한다. | 중복·누락 없이 다음 목록이 표시되고 정렬 기준이 유지된다. |
| [ ] | 관리자가 패치노트를 작성한 뒤 공개·비공개 상태를 각각 적용한다. | 공개 항목만 사용자 목록에 노출되고 비공개 항목은 관리자 화면에서만 관리된다. |

### 권장 검증

| 확인 | 행동 | 기대 결과 |
|------|------|-----------|
| [ ] | 관리자에서 공개 패치노트의 내용을 수정한다. | 사용자 목록에 수정 내용이 반영되고 순서·공개 상태가 의도대로 유지된다. |
| [ ] | 일반 사용자로 관리자 패치노트 주소에 접근한다. | 관리자 권한이 필요한 기능이 노출되거나 실행되지 않는다. |
| [ ] | 모바일 화면에서 아이콘과 긴 수정 목록을 확인한다. | 아이콘 접근이 쉽고 내용이 가로로 잘리거나 겹치지 않는다. |
