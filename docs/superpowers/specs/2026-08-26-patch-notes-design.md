# TPMP 패치노트 기능 설계

## 1. 배경과 목표

사용자 문의를 반영해 배포한 수정 사항을 서비스 안에서 전달할 전용 창구가 필요하다. 관리자는 패치노트를 직접 작성·수정·공개할 수 있어야 하고, 사용자는 학습 흐름을 방해받지 않으면서 필요할 때 언제든 최신 변경 내역을 확인할 수 있어야 한다.

이번 기능의 목표는 다음과 같다.

- 사용자 헤더에서 한 번의 클릭으로 패치노트 목록에 접근한다.
- 사용자는 별도 상세 페이지 없이 최신순 목록에서 변경 내용을 바로 읽는다.
- 관리자는 제목, 버전, 수정 내용, 공개 여부를 관리한다.
- 수정 내용은 기존 리치텍스트 편집·렌더링 자산을 재사용한다.
- 사용자별 읽음 상태나 알림 배지는 만들지 않는다.

## 2. 확정된 제품 결정

- 사용자 진입점은 도움말 메뉴가 아니라 상단 헤더의 독립된 패치노트 아이콘이다.
- 아이콘은 데스크톱과 모바일에 항상 표시한다.
- 아이콘 클릭 시 `/user/patch-notes` 목록 페이지로 바로 이동한다.
- 목록의 각 카드에 버전, 제목, 게시일, 수정 내용을 모두 표시한다.
- 사용자용 상세 페이지와 상세 조회 API는 만들지 않는다.
- 사용자별 읽음 상태, 미확인 숫자 배지, 로그인 팝업은 만들지 않는다.
- 관리자는 기존 `RichTextEditor`로 수정 내용을 작성한다.
- 공개 예약, 중요도, 분류, 첨부파일, 댓글 기능은 이번 범위에서 제외한다.

## 3. 데이터 모델

신규 `patch_notes` 테이블과 `PatchNote` 엔티티를 추가한다. 엔티티는 `BaseEntity`를 상속해 프로젝트의 감사·소프트 삭제 규칙을 따른다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGINT | PK, 자동 증가 | 패치노트 식별자 |
| `title` | VARCHAR(200) | NOT NULL | 사용자에게 표시할 제목 |
| `version` | VARCHAR(50) | NOT NULL | `v1.2.0`, `2026.08 업데이트` 등 자유 형식 |
| `content` | TEXT | NOT NULL | 리치텍스트 HTML 수정 내용 |
| `published_yn` | VARCHAR(1) | NOT NULL, 기본 `N` | 공개 여부 |
| `published_dt` | TIMESTAMP | NULL 허용 | 최초 공개 시각 |
| `create_dt` | TIMESTAMP | NOT NULL | 생성 시각 |
| `create_uno` | BIGINT | NOT NULL | 생성 관리자 번호 |
| `modified_dt` | TIMESTAMP | NOT NULL | 최종 수정 시각 |
| `modified_uno` | BIGINT | NOT NULL | 최종 수정 관리자 번호 |
| `del_yn` | VARCHAR(1) | NOT NULL, 기본 `N` | 소프트 삭제 여부 |
| `use_yn` | VARCHAR(1) | NOT NULL, 기본 `Y` | 레코드 활성 여부 |

`published_yn`은 콘텐츠 공개 상태, `use_yn`은 공통 엔티티의 운영 활성 상태로 의미를 분리한다. 이번 관리자 UI에서는 `use_yn`을 직접 조작하지 않는다.

공개 상태 전이 규칙은 다음과 같다.

- 비공개로 생성하면 `published_yn='N'`, `published_dt=NULL`이다.
- 처음 공개할 때 `published_dt`를 현재 시각으로 기록한다.
- 공개 글의 내용을 수정하거나 비공개로 전환해도 기존 `published_dt`는 유지한다.
- 비공개 글을 다시 공개해도 최초 게시일을 유지한다.
- 삭제는 물리 삭제하지 않고 `del_yn='Y'`로 처리한다.

사용자 목록 조회 성능을 위해 `(del_yn, published_yn, published_dt DESC)` 조회에 맞는 인덱스를 추가한다. 버전은 표시용 자유 문자열이므로 유일성 제약을 두지 않는다.

## 4. 백엔드 구조와 API

프로젝트 규칙에 따라 Controller → Service → Repository 3계층을 구성한다.

### 사용자 API

`GET /api/user/patch-notes?page=0&size=10`

- 인증된 USER 또는 ADMIN이 호출할 수 있다.
- `del_yn='N'`, `use_yn='Y'`, `published_yn='Y'`인 글만 반환한다.
- `published_dt DESC`, 동률이면 `id DESC`로 정렬한다.
- 응답은 `ApiResponse<Page<PatchNoteResponse>>` 형식이다.
- 목록 카드가 전체 내용을 표시하므로 별도 사용자 상세 API는 제공하지 않는다.

### 관리자 API

- `GET /api/admin/patch-notes?page=0&size=10` — 삭제되지 않은 전체 목록
- `GET /api/admin/patch-notes/{id}` — 수정 화면용 단건 조회
- `POST /api/admin/patch-notes` — 등록
- `PUT /api/admin/patch-notes/{id}` — 제목·버전·내용·공개 여부 수정
- `PATCH /api/admin/patch-notes/{id}/publication` — 공개 여부 변경
- `DELETE /api/admin/patch-notes/{id}` — 소프트 삭제

관리자 엔드포인트는 `/api/admin/**` 보안 규칙과 `@PreAuthorize("hasRole('ADMIN')")`를 모두 적용한다. 컨트롤러는 인증 이메일을 서비스로 전달하고, 서비스는 사용자 저장소에서 관리자 번호를 조회해 감사 필드에 기록한다.

요청 DTO 검증 기준은 다음과 같다.

- 제목: 공백 불가, 최대 200자
- 버전: 공백 불가, 최대 50자
- 내용: 공백 불가
- 공개 여부: 필수 boolean

존재하지 않거나 삭제된 관리자 대상에는 `PATCH_NOTE_NOT_FOUND`를 반환한다. 사용자 API는 비공개·비활성·삭제 글을 애초에 목록에서 제외한다.

## 5. 프론트엔드 구성

### 사용자 헤더 아이콘

`UserLayoutShell`의 우측 영역에서 테마 전환 버튼 옆에 확성기 아이콘 링크를 배치한다.

- 링크: `/user/patch-notes`
- 접근성 이름: `패치노트 보기`
- 데스크톱과 모바일에서 동일하게 표시
- 활성 경로에서는 인디고 계열 배경·텍스트로 현재 위치를 표현
- 읽음 숫자나 `NEW` 표시는 없음

이 페이지는 동적 메뉴 권한과 독립된 공통 사용자 기능이므로 `UserLayoutShell`의 항상 허용 경로에 `/user/patch-notes`를 추가한다. 사용자 메뉴 시드에는 별도 항목을 추가하지 않는다.

### 사용자 목록 페이지

`/user/patch-notes`에서 최신순 카드 목록을 표시한다.

- 페이지 제목과 짧은 설명
- 카드 헤더: 버전 배지, 제목, 게시일
- 카드 본문: 기존 `RichContent`로 전체 수정 내용 렌더링
- 로딩: 기존 `CardListSkeleton` 재사용
- 빈 상태: `아직 등록된 패치노트가 없습니다.`
- 페이지네이션: 기존 `Pagination` 컴포넌트 재사용
- 라이트·다크 모드 모두 지원

저장된 HTML은 화면에서 직접 주입하지 않고 `RichContent`를 통해 DOMPurify로 정화한 뒤 렌더링한다.

### 관리자 화면

관리자 사이드바에 `패치노트 관리` 메뉴를 추가한다.

- `/admin/patch-notes` — 목록
- `/admin/patch-notes/new` — 등록
- `/admin/patch-notes/{id}/edit` — 수정

목록은 버전, 제목, 공개 상태, 게시일, 수정일과 작업 버튼을 보여준다. 로딩 중에는 `TableSkeleton`, 빈 상태에는 안내 문구를 사용한다. 공개 상태 전환과 삭제는 실패 시 기존 `extractApiErrorMessage` 패턴으로 오류를 표시하고, 삭제 전 확인을 받는다.

등록·수정 화면은 제목, 버전, 수정 내용, 공개 여부를 입력한다. 수정 내용에는 기존 `RichTextEditor`를 사용한다. 클라이언트는 태그를 제외한 실제 텍스트가 비어 있는지도 검사하고, 서버 오류 메시지를 사용자에게 표시한다.

관리자 메뉴는 `DataInitializer`의 메뉴 시드와 `AdminLayoutShell`의 fallback 메뉴에 함께 추가한다. 신규 아이콘 키도 양쪽 레이아웃의 정적 아이콘 맵에 반영한다.

## 6. 데이터 흐름

1. 관리자가 등록 화면에서 내용을 입력하고 저장한다.
2. 프론트엔드는 관리자 API로 검증된 요청을 보낸다.
3. 서비스는 관리자 번호를 확인하고 엔티티 감사값과 최초 게시일 규칙을 적용한다.
4. 공개 글은 사용자 목록 API의 다음 조회부터 최신순으로 노출된다.
5. 사용자는 헤더 아이콘으로 목록 페이지에 진입해 카드 안에서 전체 내용을 확인한다.

별도 캐시나 실시간 푸시는 사용하지 않는다. 공개/수정 결과는 다음 목록 요청부터 반영한다.

## 7. DB 배포와 기존 데이터

신규 테이블과 인덱스 DDL은 `docs/db-migration/20260826_01_create_patch_notes.sql`에 재실행 가능한 형태로 추가하고, `docs/sql/README.md`의 델타 목록도 함께 갱신한다. 운영 환경은 `ddl-auto=validate`이므로 애플리케이션 배포 전에 이 마이그레이션이 적용되어야 한다. 로컬 `ddl-auto=update`만 믿고 배포하지 않는다.

초기 패치노트 데이터는 자동으로 게시하지 않는다. 기능 배포 후 관리자가 실제 사용자 공지 내용을 작성해 공개한다. 따라서 사용자 화면은 빈 상태도 완성된 UI로 제공해야 한다.

## 8. 오류 처리와 보안

- 관리자만 등록·수정·공개 전환·삭제할 수 있다.
- 사용자 API는 인증된 계정에만 공개한다.
- 사용자 응답은 삭제·비공개·비활성 콘텐츠를 포함하지 않는다.
- 리치텍스트 HTML은 `RichContent`의 정화 경로로만 렌더링한다.
- 서버 검증 실패는 `ApiResponse` 오류 형식을 유지한다.
- 목록 조회 실패 시 기존 페이지 패턴에 맞는 오류 상태와 재시도 가능한 안내를 제공한다.
- 공개 상태 변경과 삭제는 낙관적으로 화면에서 먼저 바꾸지 않고 서버 성공 후 상태를 갱신한다.

## 9. 검증 전략

### 백엔드

- 비공개 생성 시 게시일이 비어 있는지 확인
- 최초 공개 시 게시일이 설정되는지 확인
- 비공개 후 재공개해도 최초 게시일이 유지되는지 확인
- 사용자 목록이 공개·활성·미삭제 글만 최신순으로 반환하는지 확인
- 삭제가 소프트 삭제인지 확인
- 일반 사용자가 관리자 API에 접근할 수 없는지 확인
- `./gradlew test`

### 프론트엔드

- 헤더 아이콘이 데스크톱·모바일에서 표시되고 목록 페이지로 이동하는지 확인
- 사용자 목록의 로딩·빈 상태·카드·페이지네이션 확인
- 관리자 등록·수정·공개 전환·삭제 흐름 확인
- 리치텍스트가 라이트·다크 모드에서 안전하고 읽기 쉽게 렌더링되는지 확인
- `npx tsc --noEmit`
- `npm test -- --watch=false`
- `npm run build`

### 프로젝트 기록

코드 변경 후 관리자/사용자 및 프론트엔드/백엔드 범위에 맞는 `docs/history/` 파일을 작성한다. DB·API·다중 파일 변경이므로 단계 경계마다 `docs/agent-handoff/CURRENT.md`를 갱신한다.

## 10. 완료 기준

- 관리자가 패치노트를 등록하고 공개 상태를 제어할 수 있다.
- 공개 패치노트만 사용자 목록에 최신순으로 표시된다.
- 사용자는 어떤 화면에서도 헤더 아이콘을 통해 패치노트 목록으로 이동할 수 있다.
- 사용자 목록에서 별도 상세 이동 없이 전체 수정 내용을 읽을 수 있다.
- 사용자별 읽음 상태나 불필요한 알림 UI가 없다.
- 타입체크, 프론트엔드 테스트·빌드, 백엔드 테스트가 통과한다.
