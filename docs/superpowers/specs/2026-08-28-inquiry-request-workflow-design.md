# TPMP 문의·요청 처리 및 이메일 알림 기능 설계

## 1. 배경과 목표

현재 문의 기능은 `시험`, `개념노트`, `버그 신고`처럼 발생 영역과 접수 목적을 하나의 `inquiryType`으로 표현하고, 관리자가 답변하면 곧바로 `답변 완료`가 되는 단일 답변 구조다. 이 구조로는 버그 신고·시험 개설 요청·신규 기능 요청을 일반 문의와 다른 처리 흐름으로 관리하거나, 처리 중 여러 차례 추가 정보를 주고받기 어렵다.

이번 기능의 목표는 다음과 같다.

- 접수 목적과 버그 발생 영역을 분리한다.
- 일반 문의와 처리형 요청의 종료 상태를 구분한다.
- 사용자와 관리자가 종료 전까지 여러 번 대화할 수 있게 한다.
- 신규 접수·사용자 추가 답변을 지정된 관리자 이메일로 알린다.
- 관리자 답변·최종 처리 결과는 관리자가 선택한 경우에만 문의자 이메일로 보낸다.
- 메일 실패가 문의 저장이나 상태 변경을 되돌리지 않으며, 실패 이력을 확인하고 재발송할 수 있게 한다.

## 2. 확정된 제품 결정

- 기존 `/user/inquiries`, `/admin/inquiries` 경로와 `Inquiry` 도메인을 유지해 기존 데이터·연결을 보존한다.
- 사용자와 관리자 화면의 표시 명칭은 `문의·요청`, `문의·요청 관리`로 변경한다.
- 접수 유형은 `일반 문의`, `버그 신고`, `시험 개설 요청`, `신규 기능 요청`, `기타`로 구성한다.
- 버그 신고는 `발생 영역`이 필수이고 `상세 위치/URL`은 선택이다.
- 일반 문의와 기타의 정상 종료 상태는 `답변 완료`다.
- 버그 신고·시험 개설 요청·신규 기능 요청의 정상 종료 상태는 `처리 완료`이며, 수용할 수 없는 경우 `처리 불가`를 사용한다.
- 답변 등록과 상태 변경은 독립 동작이다. 관리자 답변만으로 처리형 요청이 자동 종료되지 않는다.
- 사용자와 관리자는 접수 종료 전까지 여러 개의 메시지를 주고받을 수 있다.
- 종료된 접수에는 사용자가 메시지를 추가할 수 없다. 관리자는 `검토 중`으로 다시 열 수 있다.
- 신규 접수 및 사용자의 추가 메시지는 관리자 수신 설정이 활성화되어 있으면 등록된 모든 관리자 이메일로 자동 발송한다.
- 관리자의 중간 답변, 답변 완료, 처리 완료, 처리 불가 알림은 매번 관리자가 발송 여부를 선택한다. 체크박스 기본값은 미선택이다.
- 이메일만 지원하고 SMS는 이번 범위에서 제외한다.
- SMTP 접속 정보는 환경변수로 관리한다. 관리자 화면이나 DB에는 SMTP 비밀번호를 저장하지 않는다.

## 3. 접수 유형과 상태 전이

### 접수 유형

| 코드 | 표시명 | 발생 영역 | 정상 종료 상태 |
|---|---|---|---|
| `GENERAL_INQUIRY` | 일반 문의 | 선택 | `ANSWERED` |
| `BUG_REPORT` | 버그 신고 | 필수 | `COMPLETED` |
| `EXAM_OPENING_REQUEST` | 시험 개설 요청 | 미사용 | `COMPLETED` |
| `FEATURE_REQUEST` | 신규 기능 요청 | 선택 | `COMPLETED` |
| `OTHER` | 기타 | 선택 | `ANSWERED` |

버그 발생 영역은 기존 도메인 관리 구조에 `INQUIRY_BUG_AREA` 마스터를 추가해 관리한다. 초기값은 `로그인·계정`, `사용자 홈`, `시험정보`, `시험 풀이·결과`, `데일리 퀴즈`, `개념노트`, `풀이·연습장`, `문의·요청`, `기타`다. 비활성 영역은 신규 작성 화면에서 제외하지만 기존 접수의 값은 그대로 표시한다.

### 상태

| 코드 | 표시명 | 사용 범위 |
|---|---|---|
| `PENDING` | 접수 | 전체 |
| `IN_PROGRESS` | 검토 중 | 전체 |
| `ON_HOLD` | 보류 | 전체 |
| `ANSWERED` | 답변 완료 | 일반 문의·기타만 |
| `COMPLETED` | 처리 완료 | 버그·시험 개설·신규 기능 요청만 |
| `UNABLE_TO_PROCESS` | 처리 불가 | 버그·시험 개설·신규 기능 요청만 |

허용 전이는 다음과 같다.

- 신규 접수는 항상 `PENDING`으로 시작한다.
- 관리자는 열린 상태(`PENDING`, `IN_PROGRESS`, `ON_HOLD`) 사이를 변경할 수 있다.
- 일반 문의·기타는 열린 상태에서 `ANSWERED`로 종료할 수 있다.
- 처리형 요청은 열린 상태에서 `COMPLETED` 또는 `UNABLE_TO_PROCESS`로 종료할 수 있다.
- 관리자는 모든 종료 상태를 `IN_PROGRESS`로 다시 열 수 있다.
- 사용자의 추가 메시지는 상태를 자동으로 변경하지 않는다. 다만 `PENDING`에서 첫 관리자 답변을 저장할 때 관리자가 상태를 함께 `IN_PROGRESS`로 바꿀 수 있다.
- 접수 유형에 맞지 않는 종료 상태는 프론트엔드에서 노출하지 않고 백엔드에서도 거부한다.

## 4. 데이터 모델과 기존 데이터 이관

### `inquiries` 변경

- 기존 `inquiry_type`은 접수 목적을 나타내는 `request_type`으로 전환한다.
- `target_area` nullable 문자열을 추가한다.
- `detail_location` nullable 문자열(최대 500자)을 추가한다.
- 기존 `reply`, `replied_at`은 마이그레이션 후 제거하고 메시지 테이블로 이관한다.
- 상태 enum 허용값에 `IN_PROGRESS`, `COMPLETED`, `UNABLE_TO_PROCESS`를 추가한다.

기존 데이터는 다음 규칙으로 이관한다.

- `BUG`는 `BUG_REPORT`로 바꾸고, 발생 영역이 없으므로 `target_area='OTHER'`를 지정한다.
- `EXAM`, `CONCEPT_NOTE`, `DAILY_QUIZ`, `PRACTICE`는 `GENERAL_INQUIRY`로 바꾸고 기존 값을 `target_area`에 보존한다.
- `OTHER`는 그대로 `OTHER`를 사용한다.
- 기존 `BUG + ANSWERED`는 처리형 요청의 유효한 종료 상태인 `COMPLETED`로 바꾼다.
- 기존 답변이 있으면 작성자를 시스템 이관 관리자로 표시하는 최초 관리자 메시지로 생성하고 `replied_at`을 메시지 작성 시각으로 사용한다.

### `inquiry_messages`

양방향 대화 이력을 저장한다.

| 컬럼 | 설명 |
|---|---|
| `id` | 메시지 식별자 |
| `inquiry_id` | 접수 FK |
| `author_id` | 작성 사용자 또는 관리자 FK, `SYSTEM` 이관 메시지는 NULL 허용 |
| `author_role` | `USER`, `ADMIN`, `SYSTEM` |
| `content` | 메시지 본문 |
| `created_at` | 작성 시각 |

초기 접수의 제목·본문은 `inquiries`에 유지하고, 이후 대화만 `inquiry_messages`에 저장한다. 상세 화면은 초기 접수와 메시지를 하나의 시간순 타임라인으로 렌더링한다. 메시지에도 이미지가 필요한 재현 정보가 올 수 있으므로 기존 첨부 인프라에 `INQUIRY_MESSAGE` 참조 유형을 추가하고 메시지당 이미지 3개까지 허용한다.

### 관리자 이메일 수신 설정

전역 수신 사용 여부를 저장하는 `inquiry_notification_settings`와, 중복 제거된 복수 수신 주소를 저장하는 `inquiry_notification_recipients`를 추가한다.

- 수신 설정은 관리자만 조회·수정한다.
- 수신 주소는 최대 10개다.
- 공백을 제거하고 소문자로 정규화한 뒤 대소문자 무시 중복을 차단한다.
- 수신 사용이 활성화되려면 유효한 주소가 한 개 이상 있어야 한다.
- `SupportSettings`는 후원 링크 전용 의미를 유지하고 이번 설정에 재사용하지 않는다.

### 이메일 발송 이력

`inquiry_email_deliveries`에 발송 요청과 결과를 저장한다.

- 이벤트: `NEW_INQUIRY`, `USER_MESSAGE`, `ADMIN_MESSAGE`, `ANSWERED`, `COMPLETED`, `UNABLE_TO_PROCESS`
- 상태: `PENDING`, `SENT`, `FAILED`
- 접수, 관련 메시지, 수신자, 제목, 본문, 시도 횟수, 마지막 오류, 생성·발송 시각을 기록한다.
- 관리자 수신 설정이 꺼져 있으면 자동 관리자 알림 행을 만들지 않는다.
- 사용자가 이메일 발송을 선택하지 않은 관리자 동작도 발송 행을 만들지 않는다.
- 실패한 이력만 관리자 재발송 API로 다시 `PENDING` 처리할 수 있다.

## 5. 백엔드 구조와 API

프로젝트 규칙에 따라 Controller → Service → Repository 3계층을 유지한다. 문의 상태·대화는 `InquiryService`, 메일 설정은 `InquiryNotificationSettingsService`, 발송 이력과 전송은 `InquiryEmailService`로 책임을 분리한다.

### 사용자 API

- `GET /api/user/inquiries` — 본인 접수 목록, 접수 유형·상태 응답 포함
- `GET /api/user/inquiries/{id}` — 초기 접수와 메시지 타임라인 조회
- `POST /api/user/inquiries` — 접수 생성
- `POST /api/user/inquiries/{id}/messages` — 열린 본인 접수에 메시지·첨부 추가
- 기존 이미지 업로드 API는 초기 접수와 메시지 양쪽에서 참조할 수 있도록 확장
- 기존 삭제 API는 메시지가 없고 상태가 `PENDING`인 본인 접수에만 허용

생성 요청 검증은 제목 200자, 본문 필수, 상세 위치 500자, 첨부 최대 3개를 적용한다. `BUG_REPORT`는 활성 `INQUIRY_BUG_AREA` 코드가 반드시 필요하고, 시험 개설 요청은 발생 영역 입력을 받지 않는다.

### 관리자 API

- `GET /api/admin/inquiries` — 상태·접수 유형·발생 영역 필터와 서버 페이지네이션
- `GET /api/admin/inquiries/{id}` — 접수와 전체 타임라인 조회
- `POST /api/admin/inquiries/{id}/messages` — 관리자 중간 답변, `sendEmail` 선택값 포함
- `PATCH /api/admin/inquiries/{id}/status` — 유효한 상태로 변경, 종료 설명과 `sendEmail` 선택값 포함
- `DELETE /api/admin/inquiries/{id}` — 기존 관리자 삭제 유지
- `GET /api/admin/inquiry-notification-settings` — 관리자 수신 설정 조회
- `PUT /api/admin/inquiry-notification-settings` — 사용 여부와 복수 이메일 저장
- `GET /api/admin/inquiry-email-deliveries` — 접수별 또는 실패 상태 발송 이력 조회
- `POST /api/admin/inquiry-email-deliveries/{id}/retry` — 실패 건 재발송

종료 상태로 변경할 때 최종 안내 내용은 필수다. 서비스는 이 내용을 관리자 메시지로 먼저 저장하고 상태를 변경한 다음, `sendEmail=true`이면 동일 트랜잭션에서 `PENDING` 발송 이력을 만든다. 일반 문의 답변 완료도 같은 규칙을 사용한다.

### 이메일 실행

- Spring Mail의 범용 SMTP 설정을 사용한다.
- 호스트·포트·계정·비밀번호·TLS 여부·발신 주소는 환경변수에서 주입한다.
- 문의 저장 트랜잭션은 발송 이력 생성까지만 담당한다.
- 커밋 후 비동기 실행기가 `PENDING` 이력을 발송해 `SENT` 또는 `FAILED`로 갱신한다.
- SMTP 미설정이나 외부 장애는 접수·메시지·상태 트랜잭션을 롤백하지 않는다.
- 메일은 안전한 일반 텍스트로 작성하며 접수 번호, 유형, 제목, 변경 상태, 안내 내용, 서비스 상세 링크를 포함한다.
- 마지막 오류 메시지는 민감정보를 제거하고 길이를 제한해 저장한다.

## 6. 프론트엔드 구성

### 사용자 작성 화면

`/user/inquiries/new`에서 접수 유형을 먼저 선택한다.

- 버그 신고: 발생 영역 필수 드롭다운과 상세 위치/URL 선택 입력 표시
- 일반 문의·신규 기능 요청·기타: 필요한 경우 발생 영역 선택 입력 표시
- 시험 개설 요청: 발생 영역 입력 숨김
- 접수 유형·발생 영역은 활성 도메인 항목을 사용하고 API 실패 시 코드에 고정된 최소 fallback을 사용
- 기존 이미지 첨부, 검증, 오류 메시지 패턴 유지

### 사용자 목록·상세

- 화면 명칭을 `문의·요청`으로 변경한다.
- 목록에서 접수 유형, 발생 영역, 상태를 구분해 표시한다.
- 상세는 초기 접수와 사용자·관리자 메시지를 시간순 대화 타임라인으로 표시한다.
- 열린 접수에는 메시지 작성기와 이미지 첨부를 제공한다.
- 종료 상태에는 종료 안내와 `처리가 종료되었습니다`를 표시하고 작성기를 숨긴다.
- 목록과 상세 데이터 로딩에는 프로젝트 공통 Skeleton을 사용한다.

### 관리자 목록·상세

- 메뉴와 페이지 명칭을 `문의·요청 관리`로 변경한다.
- 목록은 서버 페이지네이션과 접수 유형·상태·발생 영역 필터를 사용한다.
- 상세 화면은 타임라인, 답변 작성기, 상태 변경 영역, 이메일 발송 이력을 보여준다.
- 중간 답변에는 `사용자에게 이메일 알림 발송` 체크박스를 제공하고 기본값은 미선택이다.
- 상태 변경은 접수 유형에 유효한 상태만 보여준다.
- 답변 완료·처리 완료·처리 불가 선택 시 최종 안내 내용과 이메일 발송 체크박스를 요구한다.
- 종료 상태에는 `다시 열기` 작업을 제공한다.
- 실패한 이메일에는 실패 사유와 `재발송` 버튼을 표시한다.
- 관리자 수신 이메일 설정은 문의·요청 관리 목록의 설정 버튼에서 `/admin/inquiries/settings`로 진입한다.
- 설정 화면에서 알림 사용 여부와 최대 10개 수신 주소를 추가·삭제한다.

## 7. 데이터 흐름

### 신규 접수 및 사용자 메시지

1. 사용자가 접수 또는 추가 메시지를 저장한다.
2. 서비스가 소유권·열린 상태·조건부 입력을 검증하고 DB에 저장한다.
3. 관리자 알림 설정이 활성화되어 있으면 각 수신자에 대한 `PENDING` 발송 이력을 같은 트랜잭션에 저장한다.
4. 커밋 후 비동기 발송기가 메일을 보내고 결과를 기록한다.
5. 메일 실패와 관계없이 사용자에게는 접수 또는 메시지 저장 성공을 반환한다.

### 관리자 답변 및 종료

1. 관리자가 답변 또는 상태 변경 내용을 입력하고 이메일 발송 여부를 선택한다.
2. 서비스가 관리자 권한과 상태 전이를 검증한다.
3. 메시지와 상태를 저장하고, 이메일 선택 시 문의자 주소로 `PENDING` 발송 이력을 만든다.
4. 커밋 후 메일 결과를 기록한다.
5. 관리자는 상세 화면에서 성공·실패 이력과 실패 건 재발송 결과를 확인한다.

## 8. 오류 처리와 보안

- 사용자 조회·메시지 추가는 접수 소유자만 가능하다.
- 종료된 접수에 대한 사용자 메시지는 `INQUIRY_CLOSED` 오류로 거부한다.
- 접수 유형과 맞지 않는 상태는 `INVALID_INQUIRY_STATUS_TRANSITION`으로 거부한다.
- 버그 발생 영역 누락·비활성 코드는 `INVALID_INQUIRY_TARGET_AREA`로 거부한다.
- 관리자 설정·발송 이력·재발송 API는 `ADMIN` 권한을 이중 확인한다.
- 첨부는 기존 이미지 확장자·용량·UUID 파일명 정책을 그대로 사용한다.
- 메일 본문은 HTML로 직접 렌더링하지 않고 일반 텍스트로 구성해 콘텐츠 삽입 위험을 줄인다.
- SMTP 인증정보와 전체 예외 스택은 API 응답·DB 발송 오류에 노출하지 않는다.
- 외부 SMTP 호출은 DB 트랜잭션 안에서 수행하지 않는다.
- 재발송은 `FAILED` 상태만 허용하며 동시에 여러 번 요청해 중복 발송되지 않도록 상태를 원자적으로 선점한다.

## 9. 배포와 설정

재실행 가능한 SQL을 `docs/db-migration/20260828_01_extend_inquiry_workflow.sql`에 추가하고 `docs/sql/README.md` 델타 목록을 갱신한다. 운영 `ddl-auto=validate` 환경에서는 애플리케이션보다 SQL을 먼저 적용해야 한다.

기존 `INQUIRY_CATEGORY` 도메인 마스터는 코드 호환을 위해 유지하되 슬레이브 값을 새 접수 유형 코드로 교체한다. 기존 영역형 값은 데이터 이관 후 신규 작성 선택지에서 비활성화하고, `INQUIRY_BUG_AREA` 마스터와 초기 영역 슬레이브를 재실행 가능하게 시드한다.

환경 예시는 실제 비밀번호 없이 다음 항목을 문서화한다.

- `MAIL_HOST`
- `MAIL_PORT`
- `MAIL_USERNAME`
- `MAIL_PASSWORD`
- `MAIL_SMTP_AUTH`
- `MAIL_STARTTLS_ENABLE`
- `MAIL_FROM_ADDRESS`
- `APP_PUBLIC_URL`

메일 설정이 없더라도 애플리케이션은 시작할 수 있어야 한다. 설정 미완료 상태에서 생성된 발송 요청은 `FAILED`로 기록하고 관리자에게 설정 확인 메시지를 보여준다.

## 12. 완료 기준

- 접수 목적과 버그 발생 영역이 분리되고 버그 영역이 필수 검증된다.
- 일반 문의는 `답변 완료`, 처리형 요청은 `처리 완료` 또는 `처리 불가`로 종료된다.
- 사용자와 관리자가 종료 전까지 답변 이력을 보존하며 양방향으로 대화한다.
- 관리자는 사용자 이메일 발송 여부를 답변·종료 동작마다 선택한다.
- 신규 접수와 사용자 추가 답변은 설정된 복수 관리자 이메일에 알림 이력이 생성된다.
- 메일 실패가 업무 데이터 저장을 롤백하지 않고 관리자에게 실패·재발송 기능을 제공한다.
- 기존 문의 데이터와 답변이 마이그레이션 후 조회된다.
- 백엔드 테스트, 프론트엔드 타입체크·테스트·빌드가 통과한다.
- 사용자·관리자 및 프론트엔드·백엔드 범위의 히스토리와 `CURRENT.md`가 갱신된다.
