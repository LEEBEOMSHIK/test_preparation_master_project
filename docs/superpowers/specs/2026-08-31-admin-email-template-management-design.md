# TPMP 관리자 이메일 템플릿 관리 및 문의 상태 알림 역할 분리 설계

## 1. 배경과 목표

현재 관리자 문의·요청 상세 화면에는 두 가지 사용자 소통 수단이 겹쳐 있다.

- `사용자 답변 작성`은 `POST /api/admin/inquiries/{id}/messages`로 관리자 메시지를 저장하고, 선택하면 같은 답변 내용을 사용자 이메일로 보낸다.
- `상태 변경`은 `PATCH /api/admin/inquiries/{id}/status`로 종료 상태를 저장하면서 `InquiryStatusUpdateRequest.message`를 또 하나의 관리자 메시지로 저장하고, 선택하면 그 내용을 상태 변경 이메일로 보낸다.

이 때문에 관리자가 답변과 상태 안내의 차이를 이해하기 어렵고, 동일한 내용이 대화 타임라인에 중복될 수 있다. 또한 상태 이메일 본문이 코드에 고정되어 있어 운영자가 안내 문구를 관리할 수 없다. 기존 PostgreSQL의 `inquiries_status_check`에는 일부 상태만 남아 있어 `COMPLETED` 같은 정상 상태 변경도 제약조건 위반 후 잘못된 `409 DOMAIN_IN_USE`로 응답한다.

이번 기능의 목표는 다음과 같다.

- 사용자 답변과 처리 상태 변경의 책임을 UI와 API에서 분리한다.
- 종료 상태 이메일은 답변 내용이 아니라 관리 가능한 상태 안내 템플릿으로 발송한다.
- 관리자에게 HTML 템플릿 편집·미리보기·연결·테스트 발송 기능을 제공한다.
- 템플릿 미설정·비활성·오류나 SMTP 장애가 문의 상태 변경을 롤백하지 않게 한다.
- 현재 DB의 문의 상태 제약조건을 애플리케이션의 6개 상태와 일치시킨다.
- 향후 다른 이메일 이벤트도 같은 템플릿·연결 구조를 확장해 사용할 수 있게 한다.

이 문서는 `2026-08-28-inquiry-request-workflow-design.md`의 문의 종료 메시지·상태 이메일 부분을 대체한다. 특히 기존 문서의 “종료 상태 변경 시 최종 안내 내용을 필수 입력하고 관리자 메시지로 저장한다”는 규칙은 더 이상 적용하지 않는다.

## 2. 확정된 제품 결정

- 템플릿 본문과 이벤트 연결을 각각 `email_templates`, `email_template_bindings`로 정규화한다.
- 한 이벤트에는 최대 하나의 템플릿을 연결하고, 하나의 템플릿은 같은 범위의 여러 이벤트가 재사용할 수 있다.
- 시스템이 정의하는 첫 이벤트는 `INQUIRY_ANSWERED`, `INQUIRY_COMPLETED`, `INQUIRY_UNABLE_TO_PROCESS` 3개다. 관리자는 이벤트 자체를 추가하거나 삭제하지 않는다.
- 3종 기본 템플릿과 초기 연결은 배포 마이그레이션에서 자동 생성한다.
- 관리자는 템플릿을 임의로 추가·복제·편집·삭제할 수 있다. 단, 하나 이상의 이벤트에 연결된 템플릿은 삭제할 수 없다.
- 연결된 템플릿도 비활성화할 수 있다. 비활성화는 업무 상태 변경을 막지 않고 해당 이메일만 막는다.
- 템플릿 관리 메뉴는 문의 설정 하위가 아니라 글로벌 관리자 사이드바의 `이메일 템플릿 관리`로 제공한다.
- 템플릿은 WYSIWYG 방식의 HTML 편집, 변수 삽입, 정화 후 HTML 미리보기를 지원한다.
- 테스트 메일의 수신자는 서버가 현재 로그인한 관리자 계정 이메일에서 결정한다. 클라이언트가 임의 수신자를 지정할 수 없다.
- 사용자 답변은 대화 메시지이며 상태를 바꾸지 않는다. 관리자는 답변 내용을 이메일로도 보낼지 선택할 수 있다.
- 처리 상태 영역은 상태만 변경한다. 종료 안내 입력과 관리자 메시지 자동 생성은 제거한다.
- 종료 상태 이메일은 사용자 답변 내용이 아니라 연결된 상태 안내 템플릿으로 발송한다.
- 관리자 답변 없이 종료 상태로 바꾸는 것은 허용하되, UI에서 한 번 확인한다.
- 템플릿이 없거나 비활성 상태면 이메일 발송만 건너뛰고 상태 변경은 성공한다.
- 상태 변경 응답은 이메일 처리 결과를 함께 반환해 관리자가 발송 여부와 미발송 이유를 즉시 알 수 있게 한다.

## 3. 범위와 제외 범위

### 포함

- 이메일 템플릿·이벤트 연결 DB 모델과 관리자 CRUD API
- 3종 문의 종료 상태 템플릿 자동 생성·초기 연결
- 관리자 템플릿 목록·편집·연결 화면과 글로벌 사이드바 메뉴
- HTML 정화, 변수 검증·치환, 일반 텍스트 대체 본문 생성
- 현재 관리자 이메일로 테스트 발송
- 문의 사용자 답변과 상태 변경 UI·API 역할 분리
- 상태 변경 이메일 결과 응답과 템플릿 설정 안내
- `InquiryEmailDelivery`의 HTML 본문 스냅샷·발송 지원
- PostgreSQL 문의 상태 체크 제약조건 보정

### 제외

- 관리자가 시스템 이벤트를 임의로 생성·삭제하는 기능
- SMTP 계정·비밀번호를 관리자 화면에서 변경하는 기능
- SMS·푸시 알림, 사용자별 수신 거부 설정
- 이메일 첨부파일, 본문 이미지 업로드, 외부 이미지 삽입
- 원본 HTML 소스 편집과 임의 JavaScript·CSS 입력
- 기존 `NEW_INQUIRY`, `USER_MESSAGE`, `ADMIN_MESSAGE` 이메일의 템플릿 전환

마지막 항목은 3종만 먼저 관리한다는 결정에 따른 의도적인 제한이다. 기존 자동 관리자 알림과 관리자 답변 이메일은 현재 생성 방식을 유지한다. 이후 새 이메일 이벤트를 추가하거나 기존 이벤트를 템플릿 방식으로 전환할 때는 이벤트 코드와 허용 변수 범위를 먼저 정의하고, 연결된 활성 템플릿이 없으면 업무 동작은 유지하되 이메일 발송만 차단하고 템플릿 설정 안내를 제공한다.

## 4. 데이터 모델

### 4.1 `email_templates`

| 컬럼 | 제약 | 설명 |
|---|---|---|
| `id` | PK | 템플릿 식별자 |
| `name` | VARCHAR(100), NOT NULL | 관리자용 템플릿 이름 |
| `scope` | VARCHAR(50), NOT NULL | 허용 변수 집합. 초기값은 `INQUIRY_STATUS` |
| `subject_template` | VARCHAR(200), NOT NULL | 변수 토큰을 포함할 수 있는 제목 |
| `html_body` | TEXT, NOT NULL | 정화된 HTML 본문 |
| `text_body` | TEXT, NOT NULL | 정화된 HTML에서 자동 생성한 일반 텍스트 대체 본문 |
| `active` | BOOLEAN, NOT NULL | 이벤트 발송에 사용할 수 있는지 여부 |
| `system_key` | VARCHAR(80), UNIQUE, NULL 허용 | 기본 템플릿 식별자. 복제·사용자 추가 템플릿은 NULL |
| `created_by_admin_id` | FK, NULL 허용 | 생성 관리자. 시스템 시드는 NULL |
| `updated_by_admin_id` | FK, NULL 허용 | 최종 수정 관리자. 최초 시스템 시드는 NULL |
| `created_at`, `updated_at` | NOT NULL | 감사 시각 |
| `deleted_at` | NULL 허용 | 논리 삭제 시각 |
| `deleted_by_admin_id` | FK, NULL 허용 | 논리 삭제 관리자 |

템플릿 삭제는 감사 정보와 기본 시드 식별자를 보존하기 위해 논리 삭제로 처리한다. 목록·연결 선택에서는 삭제된 행을 제외한다. 삭제와 연결은 모두 대상 템플릿 행을 먼저 비관적 쓰기 잠금으로 획득한 뒤 참조·삭제 상태를 재검증한다. 따라서 삭제 확인과 실제 논리 삭제 사이에 새 연결이 끼어들 수 없고, 반대로 삭제된 템플릿이 새로 연결되지도 않는다. DB 외래키의 `ON DELETE RESTRICT`는 운영 정리 등 물리 삭제가 발생할 때의 최종 방어선이다. 삭제된 `system_key`가 남으므로 애플리케이션 재시작이나 멱등 마이그레이션이 관리자가 삭제한 기본 템플릿을 다시 노출하지 않는다.

기본 템플릿의 `초기값으로 복원`은 이름·제목·HTML 본문·일반 텍스트 본문을 코드에 정의된 기본값으로 되돌리고 `active=true`로 만든다. 이벤트 연결은 변경하지 않는다. 복제본은 새 이름과 `system_key=NULL`로 생성한다.

### 4.2 `email_template_bindings`

| 컬럼 | 제약 | 설명 |
|---|---|---|
| `event_code` | PK, VARCHAR(80) | 서버가 정의한 이메일 이벤트 코드 |
| `template_id` | FK, NOT NULL, ON DELETE RESTRICT | 연결된 활성 또는 비활성 템플릿 |
| `created_by_admin_id` | FK, NULL 허용 | 최초 연결 관리자. 시스템 초기 연결은 NULL |
| `updated_by_admin_id` | FK, NULL 허용 | 최종 변경 관리자. 시스템 초기 연결은 NULL |
| `created_at`, `updated_at` | NOT NULL | 감사 시각 |

연결 행이 없으면 해당 이벤트는 `미설정`이다. 관리자는 연결을 바꾸거나 해제할 수 있다. 같은 `event_code`는 한 행만 가지며 같은 `template_id`는 여러 이벤트가 참조할 수 있다. 이벤트와 템플릿의 `scope`가 다르면 연결을 거부한다.

### 4.3 기존 이메일 발송 이력 확장

`inquiry_email_deliveries`는 발송 당시 내용을 재현할 수 있는 스냅샷을 유지한다.

- 기존 `body`는 일반 텍스트 대체 본문으로 유지하거나 명확히 `text_body`로 이관한다.
- nullable `html_body`를 추가한다. 기존 일반 텍스트 발송 이력은 NULL이다.
- 상태 템플릿 이메일을 큐에 넣을 때 렌더링된 제목·HTML·일반 텍스트를 모두 저장한다.
- 큐 생성 후 템플릿이 수정·비활성·삭제되어도 이미 생성된 발송 이력과 실패 건 재발송 내용은 바뀌지 않는다.
- 기존 `InquiryEmailDelivery.EventType.ANSWERED`, `COMPLETED`, `UNABLE_TO_PROCESS`는 유지하고 각각 새 템플릿 이벤트 코드에 매핑한다.

## 5. 시스템 이벤트와 기본 템플릿

초기 이벤트는 모두 `INQUIRY_STATUS` 범위를 사용한다.

| 이벤트 코드 | 문의 상태 | 기존 발송 이벤트 | 기본 템플릿 이름 |
|---|---|---|---|
| `INQUIRY_ANSWERED` | `ANSWERED` | `ANSWERED` | 문의 답변 완료 안내 |
| `INQUIRY_COMPLETED` | `COMPLETED` | `COMPLETED` | 문의 처리 완료 안내 |
| `INQUIRY_UNABLE_TO_PROCESS` | `UNABLE_TO_PROCESS` | `UNABLE_TO_PROCESS` | 문의 처리 불가 안내 |

각 기본 템플릿은 다음 내용을 포함한다.

- 수신자 이름과 TPMP 안내 문구
- 문의 번호·접수 유형·제목
- 변경된 상태와 상태별 기본 설명
- 문의 상세 화면으로 이동하는 링크
- 이 메일은 상태 변경 안내이며 사용자 답변 내용이 아니라는 문구

기본 제목은 각각 다음 형식을 사용한다.

- `[TPMP] 문의 답변이 완료되었습니다: {{inquiryTitle}}`
- `[TPMP] 문의 처리가 완료되었습니다: {{inquiryTitle}}`
- `[TPMP] 문의 처리 결과를 안내드립니다: {{inquiryTitle}}`

기본 템플릿과 연결은 배포 마이그레이션에서 한 번 자동 생성한다. 마이그레이션은 `system_key`와 `event_code`를 기준으로 멱등하게 동작하고 기존 관리자의 수정값을 덮어쓰지 않는다. 논리 삭제된 기본 템플릿도 이미 생성된 것으로 간주한다.

## 6. 템플릿 변수와 렌더링 규칙

### 6.1 초기 허용 변수

`INQUIRY_STATUS` 범위는 다음 변수만 허용한다.

| 토큰 | 값 |
|---|---|
| `{{recipientName}}` | 문의자 표시 이름 |
| `{{inquiryId}}` | 문의 식별자 |
| `{{inquiryTitle}}` | 문의 제목 |
| `{{inquiryType}}` | 접수 유형 표시명 |
| `{{statusLabel}}` | 변경 상태 표시명 |
| `{{inquiryDetailUrl}}` | 서버 설정으로 생성한 사용자 문의 상세 URL |
| `{{serviceName}}` | `TPMP` |

표현식, 조건문, 반복문, 객체 접근, 함수 호출은 지원하지 않는다. 렌더러는 정해진 `{{token}}`을 단순 치환하며 SpEL, JavaScript, 임의 템플릿 표현식을 실행하지 않는다.

### 6.2 검증과 치환 순서

1. 저장 요청에서 제목·HTML의 토큰을 추출한다.
2. 선택한 `scope`의 허용 목록에 없는 토큰이 하나라도 있으면 `400 EMAIL_TEMPLATE_INVALID_VARIABLE`로 저장을 거부한다.
3. 허용 토큰을 임시 안전 표식으로 보호한 뒤 HTML 허용 목록 정화를 수행하고 토큰을 복원한다.
4. 정화된 HTML에서 `text_body`를 생성해 함께 저장한다.
5. 발송 시 DB의 정화된 템플릿을 읽고 모든 변수 값을 HTML 이스케이프해 치환한다.
6. `inquiryDetailUrl`은 서버의 `APP_PUBLIC_URL`과 문의 ID로만 생성한다. 링크 속성에 사용할 때도 `http`·`https` 프로토콜과 같은 호스트 정책을 재검증한다.
7. 치환된 최종 HTML을 다시 정화하고, 최종 일반 텍스트 본문도 생성한다.
8. 제목은 모든 CR/LF를 저장 단계에서 거부하고 렌더링 후에도 다시 검사해 헤더 인젝션을 방지한다.

저장 정화와 발송 직전 정화를 모두 수행해 기존 데이터 오염과 렌더링 값 삽입을 이중 방어한다. HTML 정화에는 OWASP Java HTML Sanitizer를 사용하고, 초기 허용 목록은 문단·줄바꿈·제목·강조·인용·목록·표·안전한 링크 같은 의미 요소로 제한한다. `script`, `iframe`, `object`, `embed`, 폼, 이벤트 속성, `style` 태그, 임의 인라인 CSS, `javascript:`·`data:` URL, 외부 이미지는 제거한다. 관리 화면 미리보기는 서버가 반환한 정화 HTML만 `RichContent`로 렌더링한다.

## 7. 백엔드 구성과 API

프로젝트 규칙에 따라 Controller → Service → Repository 계층을 유지한다.

- `EmailTemplateController` → `EmailTemplateService` → `EmailTemplateRepository`
- `EmailTemplateBindingController` → `EmailTemplateBindingService` → `EmailTemplateBindingRepository`
- `EmailTemplateRenderer`는 변수 검증·HTML 정화·치환·일반 텍스트 생성을 전담한다.
- `InquiryEmailService`는 상태 이벤트를 템플릿 이벤트로 매핑하고 렌더링 결과를 `InquiryEmailDelivery` 스냅샷으로 큐에 저장한다.
- `InquiryEmailDispatcher`는 HTML이 있으면 `MimeMessage`의 `text/plain`·`text/html` 멀티파트로, 없으면 기존 일반 텍스트 방식으로 발송한다.

### 7.1 템플릿 API

| 메서드·경로 | 동작 |
|---|---|
| `GET /api/admin/email-templates` | 검색·활성 상태·scope 조건과 페이지네이션으로 목록 조회 |
| `GET /api/admin/email-templates/{id}` | 편집 상세와 허용 변수, 연결 이벤트 조회 |
| `POST /api/admin/email-templates` | 템플릿 생성 |
| `PUT /api/admin/email-templates/{id}` | 이름·제목·HTML·활성 상태 수정 |
| `POST /api/admin/email-templates/{id}/clone` | 사용자 템플릿으로 복제 |
| `POST /api/admin/email-templates/{id}/reset-default` | `system_key`가 있는 기본 템플릿 초기화 |
| `DELETE /api/admin/email-templates/{id}` | 연결되지 않은 템플릿 논리 삭제 |
| `POST /api/admin/email-templates/{id}/test-send` | 현재 관리자 이메일로 샘플 렌더링 테스트 발송 |

목록·상세 응답에는 `referenceCount`, `referencedEvents`, `deletable`, `defaultTemplate`, `allowedVariables`를 포함한다. 테스트 발송은 템플릿이 비활성이어도 편집 검증을 위해 허용하되, 삭제된 템플릿은 허용하지 않는다. 테스트 수신 이메일은 요청 DTO에 받지 않고 인증된 관리자 계정에서 조회한다. 샘플 데이터임을 제목과 본문에 명확히 표시한다.

테스트 발송은 문의 이메일 이력에 넣지 않는다. 서버의 구조화된 감사 로그에 관리자 ID, 템플릿 ID, 수신 이메일의 마스킹 값, 성공·실패, 시각만 남기며 HTML 본문과 SMTP 인증정보는 기록하지 않는다. 테스트 API는 실제 SMTP 결과를 확인할 수 있도록 동기 발송하고 실패 시 상태 변경 같은 업무 트랜잭션과 무관한 명시적 오류를 반환한다.

### 7.2 연결 API

| 메서드·경로 | 동작 |
|---|---|
| `GET /api/admin/email-template-bindings` | 서버 정의 이벤트와 현재 연결·활성·발송 가능 상태 조회 |
| `PUT /api/admin/email-template-bindings/{eventCode}` | 호환되는 템플릿으로 연결 또는 교체 |
| `DELETE /api/admin/email-template-bindings/{eventCode}` | 연결 해제 후 미설정 상태로 전환 |

연결 API는 서버가 정의하지 않은 이벤트를 거부하고 삭제·비활성 템플릿 또는 scope가 다른 템플릿 연결을 거부한다. 이미 연결된 템플릿을 이후 비활성화하는 것은 허용한다.

### 7.3 문의 상태 변경 API

`InquiryStatusUpdateRequest`는 `status`, `sendEmail`만 받도록 변경하고 `message`를 제거한다. 종료 상태 변경도 `InquiryMessage`를 생성하지 않는다.

`PATCH /api/admin/inquiries/{id}/status`의 응답은 기존 `InquiryDetailResponse` 단독 응답 대신 다음 정보를 가진 `InquiryStatusUpdateResponse`를 반환한다.

- `inquiry`: 갱신된 `InquiryDetailResponse`
- `emailOutcome`: 이메일 처리 결과 코드
- `emailMessage`: 관리자에게 표시할 안전한 설명
- `templateSettingsUrl`: 설정이 필요할 때 `/admin/email-templates?tab=bindings`

이메일 결과 코드는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `NOT_REQUESTED` | 관리자가 이메일 발송을 선택하지 않음 |
| `QUEUED` | 렌더링된 이메일 발송 이력을 큐에 저장함 |
| `SKIPPED_TEMPLATE_MISSING` | 이벤트에 연결된 템플릿이 없음 |
| `SKIPPED_TEMPLATE_INACTIVE` | 연결된 템플릿이 비활성 상태 |
| `SKIPPED_TEMPLATE_INVALID` | 저장 데이터 손상 등으로 안전하게 렌더링할 수 없음 |

상태 변경과 이메일 큐 생성은 결과를 분리한다. 상태 전이와 상태 저장이 먼저 성공하며, 템플릿 문제는 상태 트랜잭션을 실패시키지 않는다. `QUEUED` 이후의 SMTP 실패는 기존 이메일 발송 이력에서 `FAILED`로 확인하고 재발송한다. 열린 상태 변경이나 종료 상태에서 다시 열기는 상태 이메일 대상이 아니므로 클라이언트가 `sendEmail=true`를 보내더라도 `NOT_REQUESTED`로 처리한다.

## 8. 관리자 화면 설계

### 8.1 글로벌 메뉴와 라우트

- `AdminLayoutShell`의 관리자 사이드바와 DB 관리자 메뉴 시드에 `이메일 템플릿 관리`를 독립 메뉴로 추가한다.
- 기본 경로는 `/admin/email-templates`다.
- `getPageTitle`과 메뉴 권한 설정에도 같은 경로를 등록한다.
- 목록과 연결 관리는 `/admin/email-templates?tab=templates|bindings` 두 탭으로 제공한다.
- 신규 등록은 `/admin/email-templates/new`, 수정은 `/admin/email-templates/{id}/edit` 경로를 사용한다.

### 8.2 템플릿 탭

- 이름·scope·활성 상태 검색 조건과 페이지네이션 목록
- 연결 이벤트와 참조 개수 표시
- 등록·복제·편집·활성화·비활성화 작업
- 기본 템플릿의 `초기값으로 복원` 작업
- 연결된 행은 삭제 버튼을 비활성화하고 사용 중인 이벤트를 표시
- 삭제 API가 경합으로 409를 반환하면 현재 참조 위치와 함께 다시 안내
- 데이터 로딩에는 공통 `TableSkeleton`을 사용하고, 로딩 종료 후 데이터가 없을 때만 빈 상태를 표시

### 8.3 편집 화면

- 템플릿 이름
- 템플릿 범위 선택. 초기 범위는 `문의 상태 변경`만 제공
- 제목
- 기존 `RichTextEditor`를 사용한 HTML 본문 편집
- 현재 범위에서 사용할 수 있는 변수 버튼과 커서 위치 삽입
- 서버 정화 결과를 사용하는 HTML 미리보기
- 현재 로그인 관리자 이메일을 표시하는 테스트 발송 버튼

저장 전 프론트엔드 검증은 필수값과 길이, 알려진 변수 표시를 돕는 역할만 한다. 허용 변수와 HTML 안전성의 최종 판단은 백엔드가 수행한다. 서버가 제거한 HTML이 있으면 저장 성공 후 정화된 결과를 편집기와 미리보기에 다시 반영해 실제 발송 내용을 숨기지 않는다.

### 8.4 연결 탭

서버 정의 이벤트 3개를 고정 행으로 표시한다.

- 답변 완료
- 처리 완료
- 처리 불가

각 행에서 같은 scope의 삭제되지 않은 템플릿을 선택한다. 비활성 템플릿이 이미 연결된 경우 선택값은 유지하되 `이메일 발송 중지됨`을 명확히 표시한다. 연결 해제를 지원하며, 미설정·비활성 상태에는 문의 상태 변경 이메일이 발송되지 않는다는 설명을 표시한다.

### 8.5 문의 상세 역할 분리

`/admin/inquiries/{id}`의 두 작업 영역은 다음처럼 분리한다.

#### 사용자에게 답변

- 제목을 `사용자에게 답변`으로 명확히 표시한다.
- 입력 내용이 문의 타임라인에 관리자 답변으로 추가된다는 설명을 제공한다.
- 기존 `InquiryMessageComposer`의 첨부와 `이 답변 내용을 이메일로도 발송` 선택을 유지한다.
- 답변 등록은 상태를 변경하지 않는다.

#### 처리 상태

- 접수 유형에 허용된 상태만 선택한다.
- 기존 종료 안내 입력 필드와 관리자 메시지 생성 동작을 제거한다.
- 열린 상태 간 변경에는 이메일 선택을 표시하지 않는다.
- `ANSWERED`, `COMPLETED`, `UNABLE_TO_PROCESS`로 변경할 때만 `상태 변경 안내 이메일 발송` 선택을 표시한다.
- 연결된 활성 템플릿이 없으면 체크박스를 비활성화하고 미설정·비활성 이유와 `이메일 템플릿 관리` 바로가기를 표시한다.
- 버튼 문구는 `답변 완료로 변경`, `처리 완료로 변경`, `처리 불가로 변경`처럼 선택 상태를 포함한다.
- 관리자 답변 메시지가 하나도 없는 상태에서 종료하려 하면 “사용자에게 별도 답변을 등록하지 않고 상태를 종료합니다” 확인 모달을 한 번 표시한다. 확인하면 변경하며 백엔드는 이를 차단하지 않는다.
- API가 상태 변경 성공과 이메일 미발송 결과를 함께 반환하면 성공 알림과 미발송 경고를 동시에 표시한다.

## 9. 이메일 처리 흐름

### 9.1 상태 변경 이메일

1. 관리자가 종료 상태와 이메일 발송 여부를 제출한다.
2. `InquiryService`가 접수 유형별 상태 전이를 검증하고 상태를 저장한다.
3. `sendEmail=false`면 `NOT_REQUESTED`를 반환한다.
4. `sendEmail=true`면 상태를 템플릿 이벤트 코드로 변환하고 연결을 조회한다.
5. 연결 없음·비활성·안전 렌더링 실패는 각각의 `SKIPPED_*` 결과로 기록·응답하며 상태 저장은 유지한다.
6. 렌더링에 성공하면 제목·HTML·일반 텍스트 스냅샷으로 `PENDING` 발송 이력을 만들고 `QUEUED`를 반환한다.
7. 커밋 후 기존 비동기 발송기가 전송해 `SENT` 또는 `FAILED`로 갱신한다.

템플릿 렌더링 실패를 상태 트랜잭션과 분리하기 위해 서비스는 이메일 결과를 값 객체로 반환하고, 예상 가능한 템플릿 미설정·비활성·검증 오류를 업무 예외로 다시 던지지 않는다. DB 연결 장애처럼 상태 저장 자체의 일관성을 보장할 수 없는 오류는 기존 전역 오류 처리 정책을 따른다.

### 9.2 사용자 답변 이메일

관리자 메시지는 기존처럼 먼저 대화 타임라인에 저장한다. 관리자가 이메일 발송을 선택하면 `InquiryEmailDelivery.EventType.ADMIN_MESSAGE`를 사용해 동일한 답변 내용을 이메일로 큐에 넣는다. 이 동작은 상태를 바꾸지 않으며 이번 단계에서는 상태 템플릿 연결을 요구하지 않는다.

## 10. 오류 처리와 보안

### 10.1 오류 코드

| 코드 | HTTP | 사용 조건 |
|---|---:|---|
| `EMAIL_TEMPLATE_NOT_FOUND` | 404 | 템플릿이 없거나 삭제됨 |
| `EMAIL_TEMPLATE_IN_USE` | 409 | 하나 이상의 이벤트가 참조하는 템플릿 삭제 시도 |
| `EMAIL_TEMPLATE_INVALID_VARIABLE` | 400 | scope에 없는 변수 사용 |
| `EMAIL_TEMPLATE_SCOPE_MISMATCH` | 400 | 이벤트와 템플릿 범위 불일치 |
| `EMAIL_TEMPLATE_INVALID_CONTENT` | 400 | 제목·HTML 길이, 빈 본문, CR/LF 등 안전 검증 실패 |
| `EMAIL_TEMPLATE_TEST_SEND_FAILED` | 502 | 테스트 SMTP 발송 실패 |
| `EMAIL_TEMPLATE_EVENT_NOT_FOUND` | 404 | 서버가 정의하지 않은 이벤트 코드 |

`EMAIL_TEMPLATE_IN_USE` 응답에는 관리자용 참조 이벤트 코드와 표시명을 포함한다. 삭제와 연결 서비스는 템플릿 행을 같은 순서로 잠그고 참조·삭제 상태를 다시 확인해 경합을 제어한다. 이미 연결된 템플릿 삭제는 명시적으로 `EMAIL_TEMPLATE_IN_USE`로 변환하며 일반적인 `DOMAIN_IN_USE` 문구로 숨기지 않는다. `ON DELETE RESTRICT`는 물리 삭제 경로의 안전장치로 유지한다.

### 10.2 권한과 콘텐츠 보안

- 모든 템플릿·연결 API는 현재 관리자 인증·인가 정책을 적용한다.
- 테스트 수신자는 인증 주체의 계정 이메일만 사용하며 request body의 주소 입력을 받지 않는다.
- 관리자 ID와 이메일은 클라이언트가 전달한 값이 아니라 인증 컨텍스트와 DB 사용자 정보에서 구한다.
- HTML은 저장·발송 전 두 번 정화하고 변수 값은 문맥에 맞게 이스케이프한다.
- 제목 CR/LF, 위험한 링크 프로토콜, 이벤트 핸들러, 실행·임베드 요소를 차단한다.
- SMTP 비밀번호, 전체 예외 스택, 원본 악성 HTML은 API·로그·발송 이력 오류에 노출하지 않는다.
- 테스트 메일 로그의 이메일은 마스킹하고 본문은 기록하지 않는다.
- 템플릿 미설정·비활성은 권한 오류나 상태 변경 실패로 가장하지 않고 명시적인 이메일 결과로 전달한다.

## 11. DB 마이그레이션과 호환성

### 11.1 템플릿 스키마와 초기 데이터

재실행 가능한 SQL 마이그레이션을 추가해 다음을 수행한다.

- `email_templates`, `email_template_bindings`와 인덱스·외래키 생성
- 기존 `inquiry_email_deliveries`에 HTML 본문 저장 컬럼 추가
- 3종 기본 템플릿 삽입
- 3종 이벤트의 초기 연결 삽입
- 기존 행·관리자 수정값·논리 삭제값은 덮어쓰지 않음

운영 `ddl-auto=validate` 환경에서는 애플리케이션 배포 전에 SQL을 적용한다. 로컬 `ddl-auto=update` 환경에서도 초기 데이터는 동일한 시드 서비스 또는 러너를 통해 한 번만 생성되며, `system_key`·`event_code`로 중복을 방지한다.

### 11.2 문의 상태 체크 제약조건 보정

현재 DB의 `inquiries_status_check`는 `PENDING`, `ON_HOLD`, `ANSWERED`만 허용하지만 `Inquiry.Status`는 다음 6개다.

- `PENDING`
- `IN_PROGRESS`
- `ON_HOLD`
- `ANSWERED`
- `COMPLETED`
- `UNABLE_TO_PROCESS`

마이그레이션은 기존 제약조건 정의를 확인하고 다르면 안전하게 삭제한 뒤 위 6개 값을 허용하는 체크 제약조건으로 다시 생성한다. 이미 올바른 경우에는 변경하지 않는다.

기존 `InquirySchemaMigrationRunner`는 legacy `inquiry_type` 컬럼이 없으면 즉시 반환하므로 이 제약조건 보정까지 단순히 뒤에 추가하면 실행되지 않는다. 러너를 독립된 멱등 단계로 나누어 legacy 컬럼 제거 여부와 관계없이 상태 제약조건 검사가 실행되게 한다. SQL 마이그레이션을 기준으로 하되 이미 생성된 로컬 DB의 호환 보정을 위해 러너도 같은 6개 상태를 확인한다.

이 보정 후 정상 `COMPLETED` 상태 저장이 `DataIntegrityViolationException`과 `409 DOMAIN_IN_USE`로 잘못 변환되는 문제도 사라진다. 상태 전이 자체가 유효하지 않은 경우에는 기존 `INVALID_INQUIRY_STATUS_TRANSITION`을 사용한다.

## 12. 테스트 전략

### 12.1 백엔드 단위·통합 테스트

- 템플릿 생성·조회·수정·복제·논리 삭제
- 기본 템플릿 초기값 복원과 멱등 시드
- 연결된 템플릿 삭제의 `409 EMAIL_TEMPLATE_IN_USE`와 참조 이벤트 응답
- 비활성 템플릿 연결 유지와 신규 연결 시 삭제·scope 불일치 차단
- 지원하지 않는 변수, 빈 제목·본문, 제목 CR/LF 거부
- 악성 태그·이벤트 속성·위험 URL 제거
- 변수 HTML 이스케이프와 서버 생성 상세 URL 검증
- HTML에서 일반 텍스트 대체 본문 생성
- 테스트 메일 수신자가 현재 관리자 이메일로만 결정되는지 검증
- 테스트 SMTP 성공·실패 응답과 민감정보 비노출
- 종료 상태 변경 시 관리자 메시지가 생성되지 않는지 검증
- 템플릿 활성·미설정·비활성·손상별 `emailOutcome` 검증
- 이메일 미설정·비활성·렌더링 실패에도 문의 상태가 저장되는지 검증
- `QUEUED` 이력에 제목·HTML·일반 텍스트 스냅샷이 저장되는지 검증
- HTML 멀티파트 발송과 기존 일반 텍스트 발송 회귀 검증
- 실제 PostgreSQL에서 `inquiries_status_check`가 6개 상태를 허용하고 재실행 가능한지 검증
- 관리자 이외 사용자의 템플릿·연결 API 접근 거부
- `backend`의 `./gradlew test`

### 12.2 프론트엔드 테스트

- 템플릿 목록 Skeleton·빈 상태·검색·페이지네이션
- 등록·복제·편집·활성화·비활성화·기본값 복원
- 연결된 템플릿 삭제 버튼 비활성화와 409 경합 오류 안내
- 변수 삽입, 서버 정화 결과 반영, HTML 미리보기
- 테스트 발송 수신자가 현재 관리자 이메일로 고정되어 표시되는지 검증
- 이벤트 연결·교체·해제와 미설정·비활성 표시
- 문의 상세의 `사용자에게 답변`과 `처리 상태` 영역 설명·동작 분리
- 종료 안내 입력 제거와 상태 변경 시 메시지 미생성
- 관리자 답변 없이 종료 시 확인 모달
- 템플릿 없음·비활성 시 이메일 체크 비활성화와 설정 링크
- 상태 성공과 이메일 `SKIPPED_*` 경고의 동시 표시
- `frontend`의 `npx tsc --noEmit`, `npm test -- --watch=false`, `npm run build`

### 12.3 수동 검증

- 관리자 사이드바에서 템플릿 관리로 직접 진입
- 3종 기본 템플릿·연결 자동 생성 확인
- 각 상태 템플릿 수정 후 현재 관리자 이메일로 실제 HTML 테스트 발송
- 사용자 답변 이메일과 상태 변경 이메일의 제목·본문·타임라인 역할이 다른지 확인
- `BUG_REPORT`를 `COMPLETED`로 변경했을 때 409 없이 저장되는지 확인
- 연결 해제·비활성 상태에서 상태는 변경되고 이메일만 미발송되는지 확인
- 실패한 큐 이메일이 기존 이메일 발송 이력에서 실패·재발송 대상으로 유지되는지 확인

## 13. 완료 기준

- 관리자가 글로벌 메뉴에서 이메일 템플릿과 이벤트 연결을 언제든 관리할 수 있다.
- 3종 기본 템플릿이 자동 생성·연결되고 기존 설정을 덮어쓰지 않는다.
- 연결된 템플릿은 참조 위치가 표시된 409로 삭제가 차단되며 비활성화는 가능하다.
- 템플릿 HTML과 변수는 저장·발송 시 안전하게 처리된다.
- 테스트 메일은 현재 로그인 관리자 이메일에만 발송된다.
- 사용자 답변은 타임라인 메시지, 상태 변경은 상태와 상태 안내 이메일로 분리된다.
- 종료 상태 변경은 관리자 메시지를 자동 생성하지 않는다.
- 템플릿 문제나 이메일 장애가 문의 상태 변경을 실패시키지 않는다.
- 상태 변경 응답과 UI가 이메일 처리 결과 및 설정 경로를 명확히 안내한다.
- PostgreSQL의 6개 문의 상태가 애플리케이션과 일치하고 기존 409 문제가 재발하지 않는다.
- 백엔드 테스트와 프론트엔드 타입체크·테스트·빌드가 통과한다.
